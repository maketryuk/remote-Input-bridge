# Remote Input Bridge — Wire Protocol v1

Two channels between the Windows **sender** and the macOS **receiver**:

| Channel  | Transport   | Default port | Purpose |
|----------|-------------|--------------|---------|
| Control  | TCP         | 47821        | Handshake, pairing, authentication, heartbeat, reliable input events |
| Realtime | UDP         | 47822        | Mouse movement only (lossy, cumulative, authenticated) |

The receiver **listens**; the sender **connects**. All multi-byte integers are **big-endian**.
`protocol_version = 1`. Time values are microseconds from each host's monotonic clock
(`QueryPerformanceCounter` / `mach_absolute_time`) — they are never compared across hosts,
only echoed back for RTT measurement.

---

## 0. Discovery (UDP 47823)

Optional, unauthenticated, and outside the session: it exists so nobody has to type an address that
a DHCP lease will change.

**Probe** (Windows → directed broadcast of every local subnet, and 255.255.255.255):

| Offset | Size | Value |
|--------|------|-------|
| 0 | 4 | magic `RIBD` (0x52494244) |
| 4 | 1 | version, currently 1 |
| 5 | 251 | zero padding |

The padding is not decoration. A short probe with a long reply is a reflection amplifier — spoof
the source address and every responder helps flood a third party — so a probe shorter than 256
bytes is ignored, and a reply that would exceed the probe is not sent.

The limited broadcast alone is not enough: it follows the default route, and a VPN holding that
route makes it fail with "no route to host". The sender therefore enumerates its own interfaces and
sends to each subnet's directed broadcast as well.

**Reply** (Mac → the address that probed):

| Offset | Size | Value |
|--------|------|-------|
| 0 | 4 | magic `RIBD` |
| 4 | 1 | version, currently 1 |
| 5 | … | JSON: `name`, `host` (the `.local` name, may be empty), `tcp`, `udp`, `version` |

Discovery conveys no authority. It reveals a name and two port numbers that a port scan would have
found anyway, and a sender still has to pair with a code shown on the Mac before it can send a
single event.

## 1. Key hierarchy

```
pairing code (user-visible, 8 chars base32, 40 bit)
        │  HKDF-SHA256(salt="rib-pair-v1", info="pairing")
        ▼
   pairing key (32 B, ephemeral, valid only while Mac is in pairing mode)
        │  used once to authenticate the PAIR exchange and wrap the device key
        ▼
   device key (32 B, random, generated by the Mac, stored on both sides)
        │  HKDF-SHA256(salt=client_nonce||server_nonce, info="rib-session-v1|<sub>")
        ├──▶ tcp key     (info "...|tcp")   — frame authentication on the control channel
        └──▶ udp key     (info "...|udp")   — packet authentication on the realtime channel
```

The device key never travels in the clear: it is transported as
`device_key XOR HKDF(pairing_key, info="wrap")` together with an HMAC over the wrapped blob.

`session_id` is a random `u64` generated per session by the receiver and echoed in every
UDP packet, so a stale sender cannot inject movement into a newer session.

> **Threat model (MVP).** This authenticates and integrity-protects every input packet
> against an unpaired device and against replay. It does **not** provide confidentiality:
> keystrokes on the control channel are not encrypted. Use only on a trusted LAN.
> TLS/DTLS is planned for v2 (see README "Limitations").

## 2. Control channel framing (TCP)

Every frame is length-prefixed:

```
[u32 length][payload ... length bytes]      length <= 65536
```

### 2.1 Handshake phase (unauthenticated)

`payload` is UTF-8 JSON with a mandatory `"t"` (type) field. Unknown fields are ignored,
which is how forward-compatible capabilities are added.

### 2.2 Session phase (authenticated)

After `AUTH_OK` every frame in **both** directions is:

```
[u32 length]
  [u64 counter]        strictly increasing per direction, starts at 1
  [u8  msg_type]
  [   body      ]      length - 8 - 1 - 16 bytes
  [u8; 16 tag]         HMAC-SHA256(tcp_key, counter || msg_type || body)[0..16]
```

A frame with a bad tag, or with `counter <= last_seen_counter`, terminates the session.

## 3. Handshake

```
Windows                                     Mac
   │  HELLO                                  │
   │─────────────────────────────────────────▶│
   │                              HELLO_ACK   │
   │◀─────────────────────────────────────────│
   │                                          │
   │  (first time only)  PAIR_REQUEST         │
   │─────────────────────────────────────────▶│
   │                           PAIR_RESPONSE  │
   │◀─────────────────────────────────────────│
   │                                          │
   │  AUTH                                    │
   │─────────────────────────────────────────▶│
   │                                AUTH_OK   │
   │◀─────────────────────────────────────────│
   │  SESSION_START (binary, msg 0x01)        │
   │─────────────────────────────────────────▶│
```

### HELLO (W → M)
```json
{ "t": "HELLO", "protocol_version": 1, "client_name": "WINDOWS-PC",
  "client_id": "b3f1…(hex 16 B, stable per install)",
  "client_nonce": "hex 32 B",
  "capabilities": ["mouse_move_udp","mouse_buttons","scroll_hires","keyboard","heartbeat"] }
```

### HELLO_ACK (M → W)
```json
{ "t": "HELLO_ACK", "protocol_version": 1, "server_name": "Nikita-MBP",
  "server_nonce": "hex 32 B", "known_client": false, "pairing_mode": true,
  "capabilities": ["mouse_move_udp","mouse_buttons","scroll_hires","keyboard","heartbeat"] }
```
* `known_client` — the Mac already holds a device key for this `client_id`.
* `pairing_mode` — the Mac is currently displaying a pairing code.

### PAIR_REQUEST (W → M)  — only when `known_client == false`
```json
{ "t": "PAIR_REQUEST", "proof": "hex 32 B" }
```
`proof = HMAC-SHA256(pairing_key, "pair" || client_nonce || server_nonce)`

### PAIR_RESPONSE (M → W)
```json
{ "t": "PAIR_RESPONSE", "wrapped_key": "hex 32 B", "tag": "hex 32 B" }
```
`wrapped_key = device_key XOR HKDF(pairing_key, info="wrap")`
`tag = HMAC-SHA256(pairing_key, "wrap" || client_nonce || server_nonce || wrapped_key)`

**Neither side may store the new device key at this point.** Both commit it only after the `AUTH`
exchange below succeeds with it. Committing on `PAIR_RESPONSE` lets the two sides diverge: if the
sender never authenticates, the receiver is left holding a key the sender has never seen, and
every later connection fails with `BAD_PROOF` and no way back except pairing again. The pairing
code therefore stays valid until `AUTH` completes, so a failed attempt can simply be retried.

### AUTH (W → M)
```json
{ "t": "AUTH", "proof": "hex 32 B" }
```
`proof = HMAC-SHA256(device_key, "auth" || client_nonce || server_nonce)`

### AUTH_OK (M → W)
```json
{ "t": "AUTH_OK", "session_id": 13845729384572345, "server_proof": "hex 32 B",
  "udp_port": 47822 }
```
`server_proof = HMAC-SHA256(device_key, "auth-ack" || client_nonce || server_nonce || session_id_be)`
— proves to the sender that the receiver holds the same device key (mutual auth).

### ERROR (either direction, closes the connection)
```json
{ "t": "ERROR", "code": "VERSION_MISMATCH", "message": "server speaks protocol 1" }
```
Codes: `VERSION_MISMATCH`, `NOT_PAIRED`, `PAIRING_DISABLED`, `BAD_PROOF`, `BUSY`, `PROTOCOL_ERROR`.

A `BAD_PROOF` in reply to `AUTH` (rather than to `PAIR_REQUEST`) means the stored keys diverged.
The sender discards its stored key in that case, so the next attempt asks for a pairing code
instead of retrying a proof that can never verify.

## 4. Reliable messages (session phase)

| Type | Name | Dir | Body |
|------|------|-----|------|
| `0x01` | `SESSION_START` | W→M | `u32 mouse_interval_us`, `u8 flags` |
| `0x02` | `PING` | W→M | `u64 t_send_us` |
| `0x03` | `PONG` | M→W | `u64 t_send_us` (echo), `u64 applied_events`, `u32 udp_recv`, `u32 udp_dropped` |
| `0x04` | `TARGET_ACTIVE` | W→M | `u8 active` (1 = Mac has input, 0 = Windows) |
| `0x05` | `MOUSE_BUTTON` | W→M | `u8 button` (0 L, 1 R, 2 M, 3 X1/back, 4 X2/forward), `u8 down` |
| `0x06` | `SCROLL` | W→M | `i32 units_x`, `i32 units_y` — 120 units = one classic notch |
| `0x07` | `KEY` | W→M | `u16 hid_usage`, `u8 down`, `u8 repeat` |
| `0x08` | `MODIFIER_SYNC` | W→M | `u16 mask` (see below) — authoritative modifier state |
| `0x09` | `RELEASE_ALL` | W→M | *(empty)* — release every key and button now |
| `0x0A` | `MOUSE_MOVE_REL` | W→M | `i32 dx`, `i32 dy` — TCP fallback when UDP is disabled |
| `0x0B` | `BYE` | both | `u8 reason` (0 user, 1 shutdown, 2 protocol error, 3 session replaced) |
| `0x0C` | `EDGE_HIT` | M→W | `u8 edge` (1 = right edge) - only when edge switching is enabled |
| `0x0D` | `LOG` | W→M | `u8 level` (0 error … 4 trace), then UTF-8 text. Mirrors the sender's log into the receiver's log file |

Modifier mask bits: `0 LCtrl, 1 LShift, 2 LAlt, 3 LGui, 4 RCtrl, 5 RShift, 6 RAlt, 7 RGui`.

All of these are read from Raw Input on the sender, never from the low-level hooks: the hooks
exist only to hide input from Windows, and they are not invoked for input aimed at a
higher-integrity window.

Keys are identified by **USB HID Keyboard/Keypad usage ID** (page 0x07) — a physical key
identity, never a character (spec §14.1). The sender maps PS/2 set-1 scan codes to HID
usages; the receiver maps HID usages to macOS virtual key codes.

## 5. Realtime mouse packet (UDP)

Fixed 44 bytes, one packet per aggregation tick, only sent while movement is pending:

```
off  size  field
 0     2   magic        0x5249 ('R','I')
 2     1   version      1
 3     1   type         1 = MOUSE_MOVE
 4     8   session_id
12     8   sequence     u64, +1 per packet, never reused within a session
20     8   timestamp_us sender monotonic clock
28     4   total_x      i32, wrapping cumulative raw X since session start
32     4   total_y      i32, wrapping cumulative raw Y since session start
36     8   auth_tag     HMAC-SHA256(udp_key, bytes[0..36])[0..8]
```

Receiver rules:

1. Drop if `magic`/`version`/`type` unexpected, or `session_id` is not the live session.
2. Drop if `sequence <= last_sequence` (old or duplicate — out-of-order is tolerated
   because the payload is cumulative, so the newest packet always carries the truth).
3. Verify `auth_tag` in constant time; drop on mismatch.
4. `dx = wrapping_sub(total_x, last_total_x)`, likewise for `dy`.
   A lost packet self-heals on the next one — no accumulated position error (spec §10.2).
5. Feed `(dx, dy)` to the event scheduler, **not** straight to `CGEventPost`.
6. On `TARGET_ACTIVE(1)`, discard the stored `last_total_*` and take the next packet as a fresh
   baseline (applying no movement for it). Without this, everything the mouse did while Windows
   owned the input would be replayed as one jump the moment the Mac takes over.

**Cumulative, not incremental:** this is the whole reason a dropped datagram costs a frame
of smoothness instead of a permanent cursor offset.

## 6. Heartbeat and fail-safe

* Sender emits `PING` every `heartbeat_ms` (default 300 ms).
* Missing `PONG` for `heartbeat_timeout_ms` (default 1000 ms) ⇒ the sender declares the
  link dead, switches to `LOCAL_WINDOWS`, releases suppression, and starts reconnecting.
* Receiver treats `heartbeat_timeout_ms` of control-channel silence the same way and
  performs a full `RELEASE_ALL` locally, so no modifier can stick (spec §51).
* TCP close, `BYE`, receiver crash and process exit all take the same fail-safe path.
